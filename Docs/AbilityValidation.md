# Ability 独立包验收与检查记录

检查对象是 `Assets/Scripts/Ability`，目标是项目业务单向依赖技能包公开 API。业务可以直接使用 `Ability`、`Modifier` 和结果类型，也可以在自己的程序集实现接口、注册脚本。接入具体项目不应要求修改包源码；包不引用项目实体、资源服务或 UI。Framework 不在本次范围。

本记录区分源码验证、引擎验证和目标设备验证。测试数量不能证明所有 Dota 2 规则都已实现；先固定本包支持的规则契约，再对契约逐项验收。

最新复查为 **0.2.1 / 2026-11-05**：[缺陷、修复、回归与等工作性能对照](Audits/AbilityRuntimeAudit-2026-11-05.md)。Core 419、Business 49、Editor 91、独立消费7项通过；新增18,000次固定种子不变量操作。以下引擎/目标设备门槛仍未完成。

## 1. 架构与业务 API 的验收

在全新项目另建业务 asmdef，只引用 `Game.Ability`，完成以下流程。业务源码的增删应不要求改动包目录。

1. 自行实现 `IUnit`、`IWorld`、`IResourceOwner`、`IPresentation`；使用 `ICombatUnit` 验证精确伤害/治疗。
2. 读取项目提供的 JSON，校验并原子发布；授予、升级、禁用、查询技能。
3. 输入或 AI 调用 `EvaluateOrder` 和 `IssueOrder`；UI 查询剩余冷却、实际冷却总时长、充能与恢复时间。
4. 在业务程序集注册一个 `AbilityScript` 和一个 `ModifierScript`，与 JSON 定义组合使用。
5. 注销单位并清理战斗；验证延迟回调不会继续产生结算，效果及订阅能够释放。

通过条件：没有复制 Cube 的角色、Manager、全局单例或资源实现；没有改动包源码；业务只使用公开成员。`EvaluateOrder` 的自定义过滤/getter 必须遵守只读契约，预检不会保留资源，正式施法必须重新校验。

评审每个模块时检查：状态由谁拥有、谁可以修改、何时释放；失败结果是否可区分；回调重入后是否重新验证存活与作用域；新增技能是否只增加配置/业务脚本；公共集合和事件载荷是否允许意外修改内部状态。优先迁出上述塔防配置语义，避免将编译独立等同于职责完全通用。

## 2. 规则正确性的矩阵

每条规则写出输入、事件顺序、最终状态和边界值。用预期数值与轨迹断言，不只断言“没有抛异常”。已有 fixture 是回归基线，以下矩阵也用于发现遗漏。

| 子系统 | 必测组合与边界 | 核心不变量 |
| --- | --- | --- |
| 施法 | 单位/点/无目标；未学习/禁用；前摇/后摇/引导；队列/立即/停止；资源不足；目标中途死亡或失效 | 一次提交只扣一次费用；取消与失败遵守提交点；结束事件精确一次；队列不引用已移除实例 |
| 冷却/充能 | 0、恰好到期、长帧跨多个恢复点；冷却中属性变化；升级/重置 | 剩余量不为负；充能不超过上限；UI 分母对应本次冷却 |
| Modifier | 刷新/多实例/叠层/驱散/移除来源；创建与销毁回调再增删；属性查询嵌套 | 索引与实际集合一致；销毁精确一次；动态属性仍实时计算 |
| 时间/光环 | interval 前后及恰好到期；大 delta；进出覆盖；来源本帧失效；不同添加顺序 | 周期次数符合有效时间；不追扣创建前时间；持续覆盖不会丢脉冲；离开滞留遵守采样契约 |
| 战斗 | 攻击/技能来源与伤害类型正交；护甲/魔抗/格挡；NonLethal、反伤、HP removal；过量伤害/治疗；死亡复活 | 报告值等于实际 HP 变化；反伤不形成无界链；死亡与攻击记录不重复结算 |
| 弹道 | 追踪与直线；高速长帧；穿透；多技能同施法者；目标离场；技能/弹道/战斗清理 | 每个目标按规则只命中一次；命中归属正确；超距/超时销毁；清理后不迟到命中 |
| 定义/扩展 | JSON 未知字段/枚举/NaN/引用错误/环；混合 Provider；自定义工厂；发布失败 | 失败不破坏原注册表；外部修改不污染已发布定义；不支持机制明确报错 |
| 故障/重入 | 每个外部回调抛异常、清理引擎、移除当前对象、递归触发事件 | 清理仍完成；无重复费用和事件；预算诊断可见；旧代际不继续执行 |

扩展时用单因素边界和成对组合控制规模，再为高风险链写全路径：伤害→反伤→吸血→死亡→清理、光环→周期伤害→驱散、前摇→目标离场→队列下一技能。不能假设任意大步长与小步长等价，尤其光环覆盖采用离散采样；比较必须服从已声明的时间契约。

## 3. 随机与长序列验证

0.2.1 已落地三个独立参考模型：Modifier成员/状态、费用与绝对截止时间/充能、精确HP账本，3组固定种子共18,000操作。仍需按实际业务补充复杂技能组合、场景资源和异常注入，不能将这些小模型解释为全部行为已穷尽。

使用可保存的固定种子生成施法、更新、移除技能、增删 modifier、死亡/复活、注销和清理序列。每步比较公开快照及简单参考模型：资源只在提交点变化、HP 与有效结算一致、计时与充能有界、销毁精确一次、索引无已移除对象、清理后对象数归零。失败必须保存种子、配置、操作序列和事件轨迹，并缩减为最小回归。

对合法配置和非法 JSON 分开生成；不要让生成器和被测实现共享同一计算公式，否则可能同时犯错。将普通场景预算中止视为失败，将刻意构造的递归熔断作为有预期结果的独立用例。

## 4. Unity 与 IL2CPP 门槛（尚未运行）

1. 用 Unity 2022.3 新建空项目，解压运行时 ZIP，在 Package Manager 的 Add package from disk 中选择 `com.novorizon.ability/package.json`。只保留一种安装方式，避免同名程序集重复。
2. 从验证 ZIP 复制 `Assets/Tests/EditMode/Ability` 和根 `Data/AbilityJsonSources`（含 Validation 和 Heroes）；项目启用 Unity Test Framework。使用真实 Test Runner 运行全部 EditMode fixtures，保留 XML 和 Editor 日志。
3. 加入 PlayMode 集成场景：实际帧更新、真实单位生命周期、异步资源取消、移动/销毁表现、场景卸载及重复进入战斗。当前没有这些场景，不能声称已自动化覆盖。
4. 构建目标平台 IL2CPP Player，在所需裁剪等级下测试严格 JSON DTO、外部脚本工厂、伤害/周期/弹道、资源回调和清理。`link.xml` 存在不等于构建验证通过。

有 Editor 和测试项目时，可执行：

```sh
"$ABILITY_UNITY_EDITOR" -batchmode -projectPath "$ABILITY_TEST_PROJECT" -runTests -testPlatform EditMode -testResults "$ABILITY_RESULTS/editmode.xml" -logFile "$ABILITY_RESULTS/editmode.log"
```

变量分别为 Editor 可执行文件、测试项目绝对路径、已创建的结果目录。PlayMode 与目标构建需先补齐实际测试场景和构建入口，不能仅更换参数宣称覆盖。

## 5. 性能与内存验收

先定义目标设备、后端、帧率、同时作战规模和技能系统 CPU/GC 预算，再制定通过阈值。60 Hz 的 16.67 ms 属于整个游戏，不能全部分给技能。没有目标配置时，不给出“支持 1000 单位”或“性能足够”的结论。

| 工作负载 | 参数与要隔离的成本 |
| --- | --- |
| 查询与常规更新 | 100/500/1000 单位 × 每单位 1/3/10 modifier；静态与自定义动态属性分开 |
| 真实结算 | 实际伤害、吸血、反伤及多级 proc；分别测少量/大量监听者，记录触发次数以防少做工作 |
| 弹道 | 100/500 弹体；持续新命中、高速穿透、集中销毁；分离空间查询、规则、结算和表现 |
| 光环 | 不同源数量、重叠、多人进出；分别报告普通帧与同帧 pulse 峰值 |
| 创建与释放 | 每秒大量增删 modifier/thinker/projectile；清理全部战斗；检验池增长和引用残留 |
| 实际项目成本 | 注入真实世界查询、物理/Transform、资源和表现；先开表现，再对照关闭表现定位成本 |

在相同设备、分辨率、后端、构建和确定性负载下采样；预热后记录逐帧原始值、CPU median/P95/P99/max、GC Alloc、收集次数、峰值及存活内存、对象数、命中/事件/世界候选数量、执行预算中止。先用 Development Player/Profiler 定位，再在接近发布的构建确认预算；深度分析会影响耗时，不能直接作为最终帧率。

建议持续运行 30–60 分钟并多次清理/重建战斗，比较预热后同等空闲点的内存快照。通过条件是正常工作负载无预算中止、规则结果一致、峰值满足项目预算；清理后运行时对象和订阅归零，存活内存不持续增长。池允许有界保留容量，须与泄漏区分。

现有 .NET 数据的正确读法：1000 单位 × 3 静态 modifier 的查询加更新从 36.849 ms / 48,528,104 B 降至 0.543 ms / 24 B，说明该条路径的扫描与分配已改善。事件行没有实际 modifier 监听者；弹道行主要是初次接触后的慢速持久弹体筛选，不代表持续命中与结算。`P95Ms` 是七个采样均值的最大值，不是逐帧 P95。基线中止过的行不能用于等量工作提速比较。详见 [性能方法与原始结果](../Tools/AbilityVerification/Performance/README.md)。

## 6. 可重复的源码检查

在原仓库或验证 ZIP 的顶层使用 .NET 8：

```sh
dotnet run --project Tools/AbilityVerification/Core/AbilityTests.csproj
bash Tools/AbilityVerification/PackageSmoke/run.sh
dotnet build Tools/AbilityVerification/Performance/AbilityPerformance.csproj -c Release
DOTNET_TieredCompilation=0 dotnet Tools/AbilityVerification/Performance/bin/Release/net8.0/AbilityPerformance.dll --label current --output ability-current.json
```

0.2.1 的 Core 预期419项（0.2.0历史为316项）、PackageSmoke预期7项；具体数量会随新回归增长，以零失败和没有静默跳过为准。性能程序输出源码指纹，比较时保留配置与完整结果。可用fixture名称过滤执行，但完整验收必须运行全套。

本轮英雄范围及原作差异见 [英雄 JSON 说明](../Data/AbilityJsonSources/Heroes/README.md)，新增等级属性覆盖旧格式兼容、深复制、非法配置拒绝、实时升降级和光环传递。单位目标技能验证可见性并在拒绝时不扣费；范围/直线技能仍能命中隐藏单位，已发射风暴之锤继续跟踪。编辑器设计另见 [Odin 规划](AbilityEditorOdinPlan.md)，首版已实现于可选 Editor 包，使用与真实 Unity 交互门槛见 [编辑器指南](AbilityEditorGuide.md)。

Cube 原仓库另有 `dotnet run --project Tools/AbilityVerification/Business/BusinessTests.csproj`，预期 49 项。它不进入独立验证 ZIP，独立包不需要该业务层。

这些工具使用兼容替身，验证源码规则与公开程序集边界；不替代上述 Unity/IL2CPP/目标设备门槛。发布时保留包版本、源码提交、验收结果和未支持项；目前应视为待引擎验收的预览包。
